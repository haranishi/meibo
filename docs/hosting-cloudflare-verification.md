# Cloudflare結合検証の記録

## 2026-11-20のチーム営業版

合成の2組織で、架電リストの共有、閲覧者の権限、法人連絡先の補完、決着日を使った月次集計を確認した。復元先でも共有リストと補完した連絡先を開き、同じ月の金額を照合した。別の空DBには旧CLIで作った形式1のバックアップを復元し、形式2で取り直すと、利用者・所属・企業データが一致した。[営業機能の検証記録](../.kiro/specs/team-sales-workspace/tasks.md)

画面修正前の配布版では、合成DBを使った再起動とコンテナ再作成の後、復元を検査する過程で通常要求363件中3件が503（`outcome_unknown`）になった。この実行では復元後の全ログインを確認できなかった。発生原因と実Tursoでの再現性は未確定である。

最終イメージでは同じ試験を最後まで実行できた。再起動、再作成、自然休止からの復帰後は、以前のセッションで営業記録を開けた。空のDBに復元した後は、2組織・3権限すべてで再ログインして記録を照合した。通常のHTTP要求488件で5xxは0件だった。配布用ソース240件、Worker、イメージの全層を検査し、この案件の実DB認証情報とAccess設定の秘密値が含まれないことも確認した。[配布物の識別情報と計測値](../.kiro/specs/cloudflare-hosting/spec.json)

この実行では、検証用のHTTPS入口にTLSエラー通知が66件あった。Node.jsが同じ通知を `clientError` にも転送したため、両方のカウンターが66を示した。個別のTLSエラーの種類は記録しておらず、原因は特定できていない。

バックアップ中断の試験では、旧形式の監視CLIが現行DBを読めず、最初の試行は中断処理に入る前に終了した。監視を現行CLIに切り替えて実行すると、29要求のうちロック中のログイン2件が想定どおり503になった。再起動後も同じ所有者のロックが残り、管理者が解除すると、同じセッションで保存済みの企業を開けた。

## 2026-11-20の配備準備（チーム営業機能の追加前）

公開用Workerは未作成だった。指定したCloudflareアカウントにはContainersの利用に必要なWorkers Paidがなく、Tursoの6個のDBは管理API・CLI・保存済み設定で同じprimaryを指していた。当初はDB専用トークンが6個とも期限切れだった。同日、DB別の後継トークンで6個のprimaryへの接続と容量を確認した。配備時には、その時点で有効な認証情報と契約・招待設定を照合する。

CRM本体の試験は通常版334件とクラウド版503件が通った。最低サポート版のRust 1.89でも両構成の全ターゲットがビルド検査を通った。合成100社を使ったブラウザ試験は390・768・1440ピクセルの3画面幅で成功し、商談の受注段階と金額が再読み込み後も保持されることを別に確認した。

Apple Silicon上でLinux/amd64イメージを作成し、中のRust実行ファイルがx86-64のELFであることを確認した。同じイメージをDockerで2回起動して、合成DBへHTTPSで接続した。どちらも `/health` は200。パスワード設定では `/login` がログイン画面を返し、Cloudflare Access設定で認証情報を送らない場合は401を返した。実行ユーザーのUIDは10001、接続設定ファイルの権限は600だった。Workerの試験180件と型検査も通った。[イメージの照合と起動手順](hosting-cloudflare.md)

同じRust実行ファイルとWorkerをWranglerで起動し、HTTPS入口から合成2組織のデータを操作した。管理者・編集者・閲覧者の権限がブラウザに反映され、プロセスの再起動とコンテナの再作成を経てもセッションと活動履歴が残った。3個の新しい合成DBにバックアップを復元し、2組織の3権限すべてで再ログインして保存内容を照合した。この一連の11項目で、画面の例外、静的ファイルの取得失敗、外部へのブラウザ要求は0件だった。

別の観測で、要求を止めて約180秒後にコンテナが自然に休止した。再訪後も同じセッションで保存内容を参照できた。通常のHTTPS要求334件には5xxがなく、10月に利用者側で観測した503は合成DBで再現しなかった。[休止の観測記録](../.kiro/specs/cloudflare-hosting/spec.json)<!-- ok -->

起動確認や故障試験も含めた全工程で、合成DBの前段が転送したHTTPS要求は15,907件、転送エラーは0件だった。TLS接続に関するエラーは1件記録された。集計から発生工程や原因は特定できない。

復旧の試験では、バックアップが合成DBの保守用ロックを取得した時点でバックアップを中断した。直後のログイン要求とRust再起動後の同じ要求は503だった。終了した処理の所有者を指定して管理CLIでロックを解除すると、`/health` が200に戻り、以前のセッションで企業データを参照できた。実Tursoで起きた接続障害の原因、公開先での本人ログインと復旧は未確認。

## 2026-10-27の結合検証

以下はPR7で取り込んだRust実行物とWorker bundleの記録。実Tursoに接続したときの障害原因は、この時点では特定できなかった。

### 確認できたこと

- 実Wrangler SDKのHTTPS入口から、合成SQLDに接続する構成で、6並列要求を3回、計18件実行し、すべて200だった。
- 同じ構成のブラウザ検証は8項目を通過。2組織3権限、更新、CSRF/context拒否、旧tab、logout、3画面幅を確認した。想定外の400、資産取得失敗、外部要求、page errorは0だった。
- 別の実行でも8項目を通過し、再起動後のセッション・storage scope・保存内容を確認した。
- SDKは外部からのDocker再起動後にコンテナを再作成した。検証ではコンテナIDの維持を求めず、新しいプロセスと保存内容を確認した。
- 実Tursoのsource用secret参照と設定の一致、直接Docker CLIによるgate-statusを確認した。

### 未解決の観察

合成SQLDへの接続では、別の実行でAPIが約33秒後に503/outcome_unknownとなった。<!-- ok -->
このときDB入口はTCP接続を1件受けたが、TLSのsecureConnectionイベントは発生せず、
ECONNRESETを記録した。対応するHTTP/SQLのエラー記録はなかった。
原因は未確定だ。アプリ・SDK・検証用ネットワークをさらに切り分ける必要がある。

実Tursoへ切り替えた構成では、SDKの起動確認が30秒後に503/unavailableとなった。<!-- ok -->
その後のコンテナ内部のhealthは503/outcome_unknownだった一方、
同じコンテナのOpenSSLによるTursoへのTLS接続と証明書検証は成功した。
ブラウザ検証はhealthで停止。実Tursoを使う構成は未合格。

### 当時の保持・復旧と公開の残件

再起動後の保持は確認できた。70秒の無要求観測では休止を確認できなかった。<!-- ok -->
[公式API](https://developers.cloudflare.com/containers/api/durable-object-container/#setinactivitytimeout)の60秒はDOが非活動になった後から数える。<!-- ok -->
観測時間を延ばした試行はAPIタイムアウトで止まり、休止の再検証には至らなかった。
休止、明示的な再作成、故障gateの復旧、新DBへのrestoreは、SDK経由では未合格。
既存のnative経路での13項目成功を、この構成の証拠へ置き換えない。
