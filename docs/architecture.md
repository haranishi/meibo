# 設計の判断と捨てた案

コードを読めば分かることは書かない。ここには、コードを消したら失われる理由・実測・落とし穴だけを置く。要件と設計の全文は `.kiro/specs/list-engine/`、実測は `benchmarks.md`。

## 全体

保存は SQLite の1ファイル（WAL）。公開口は `Engine` だけで、書き込みは `&mut self`、読み取りは `&self`。依存は `types` → `houjin`・`normalize`・`shapes` → `schema` → `write`・`query`・`search`・`lists`・`erase`・`bulk` → `engine` の一方向で、`xtask`（測定と点検）を `core` は知らない。

## 判断と捨てた案

**速さは「形」で約束する。** 絞り込みの全組合せは約束できない。使われる22の形に索引の連鎖（K1〜K10）を割り当て、`INDEXED BY` で固定し、`ORDER BY` は索引の列を省かず並べる。省くと一時ソートになり、先頭50件を返すのに全件を読む。
- `INDEXED BY` は、使えない索引でもエラーにならず全走査で通る。だから守るのは実行計画の文字列（`SEARCH` と期待の索引、`TEMP B-TREE` なし）の検査と測定で、構文ではない。
- 捨てた案: 列ごとの単独索引（組合せで一時ソートになる）、SQLite の計画器まかせ（索引の選び方が統計に左右される）。

**ページ送りは辞書順に分解して引く。** 前のページの最後の行の値から「これより後」を、等号の列を固定した範囲の問い合わせに分け、近い順に集める。
- 捨てた案: 行値の比較 `(a,b,c) > (?,?,?)`。索引の範囲に使われず、位置に比例して遅い（分解は位置によらず一定）。

**状態は活動の畳み込み。** 状態・次回対応日・最終活動日は、取り消されていない活動を記録順に適用した値。追加は差分で更新し、取り消しだけ畳み直す。一括変更も1社1件の状態変更の活動として残す。除外から戻せるのは `release_exclusion` だけ。
- 捨てた案: 企業の状態を直接書き換える。履歴と食い違い、取り消しが定義できない。
- 最終活動日の「なし」は NULL でなく0。NULL にすると、活動のない企業が索引K10から落ちる（部分索引で一度踏んだ）。

**件数表（状態×電話の12行）。** 全件・状態別・電話別の件数は、書き込みと同じ確定の中の差分で保つ。`verify` が再集計と照合する。捨てた案: 毎回 `count(*)`（数百万行を数える）。

**社名検索は2本立て。** 3文字以上は全文索引（trigram、外部内容表）、2文字以下は `instr` の走査。trigram は2文字以下で0件を返すので、取りこぼしを避けるために別経路にした。
- 全文索引は登録・改名・消去の同じ確定の中で、旧キーの `'delete'` → 新キーの挿入。大量追加は終わりに `'rebuild'`。
- 除外の企業の件数は「全文索引の総数 − 除外の中の該当数」で出す。除外1社ごとに全文索引へ問い合わせる方式は、除外が増えるほど遅くなり、100万社で目標の十数倍かかった。

**追記専用と消去は両立させる。** 活動はトリガーで更新・削除を禁じ、消去の処理の中でだけ、恒久の1行表 `erase_gate` を使って `note` の NULL 化を許す。永続のトリガーは一時表を参照できないので、ゲートは一時表でなく恒久表にした。
- 消した値は、全文索引の `'rebuild'` → `VACUUM` → `wal_checkpoint(TRUNCATE)` の後で、保存ファイルと WAL から消える。消去の直後は、WAL に旧キーの断片が残る。
- 移行前の複製には消去が及ばない。文書（`DISCLAIMER.md`）に書く。

**`compact` の空き。** `VACUUM` は元のファイルの最大2倍の空きを要する（SQLite 公式）。確認は2倍で行う。

**大量追加は索引を落として、最後に作る。** 索引10本を一度落とし、企業を入れ、索引・全文索引・件数表を作り直す。1回の確定にするので、保存ファイルと WAL が同時に約同じ大きさになる。空きの確認は、見積りの2.5倍。

**耐久性は WAL＋NORMAL が既定。** アプリの強制終了では確定を保つが、電源断では直近の確定を失いうる。確定ごとの保持が要るときは FULL を選ぶ。macOS の `fsync` はドライブの書き込みキャッシュまで保証しないので、FULL では `fullfsync` も有効にする（確定1件の時間は数倍になる。測定は参考値として文書に載る）。

**書き戻し（チェックポイント）は別スレッドへ、WAL の暴走は背圧で止める。** 散らばった10万行の更新は約10万ページ（約400MB）の書き換えになり、COMMIT のたびに SQLite が行う書き戻しと同期が、書き込みの呼び出しの時間の大きな部分を占めていた（測定は `benchmarks.md`）。主の接続の自動の書き戻しを止め、専用スレッドが、溜まったページが4MiBを超えたときだけ書き戻す。活動1件の記録の最大値（書き戻しの巻き込み）も下がった。
- 背景方式は背圧を外す。重い書き込みを休まず繰り返すと、書き戻しが1回分遅れ続けて WAL を巻き戻せず、実測で7.4GBまで育った。そこで、WAL が `wal_limit_mib`（既定512）を超えたら、書き込み側が書き戻しの完了を待つ。
- 待つのは重い書き込み（見積りが上限の32分の1以上。既定なら一括変更や大量追加）だけ。活動1件の記録のような軽い書き込みは待たせない（要件5.5・5.6）。
- 休まず繰り返したときの一括変更の時間は、書き戻しの速さで決まり、`benchmarks.md` の参考値に載る。
- 捨てた案: 自動の閾値を大きくするだけ（閾値を偶然越えた小さな書き込みが、巨大な書き戻しの間止まる）、ページを小さくする（1KB・2KBで一括変更も走査も悪化）、mmap（効果なし）、索引を減らす（1本あたりの寄与は数%で、一覧の速さを失う）。
- `compact` の最後の書き戻しは、背景の書き戻しと重なると SQLite が待たずに「忙しい」を返すので、接続の待ち時間まで再試行する。

**合成データは、法人番号の未使用帯から作る。** 国税庁の構成表で、基礎番号の先頭が6・8・9は未使用。将来も保証されないので、保存先に「合成／実データ」の印を持たせ、食い違う追加を断る。

## 試験の方針

- 計画の検査: 22形の先頭ページと、50%・95%位置のページで `EXPLAIN QUERY PLAN` を期待と照合する。
- 参照実装との突き合わせ: メモリ上の単純な実装と、乱数の絞り込み・社名検索・ページ送りを比べる。
- 障害: 失敗の注入、子プロセスの強制終了、移行の失敗、壊れた複製、空きの注入。
- 変異試験: わざと誤りを入れ、試験が赤くなるかを見る。道具は `cargo xtask mutate`。
- 要件の追跡: `cargo xtask check-spec-trace` が、要件ごとに試験の注記（`REQ N.M`）を数える。別ファイルの単体試験（`tests.rs`）も数える。

## 既知の限界

- 当たりが全体の5%を超える語（例: 会社形態）の厳密な件数は、全文索引の走査量に比例して遅くなる。要件4.4は、その語に別の（緩い）目標を置いた（変更の経緯は `.kiro/specs/list-engine/amendments.md`）。速さの門は、「株式会社」と「有限会社」を通常の条件として測る。
- 一括変更は、状態を含む索引が10本あるため、1社あたりの更新が重い。件数が増えるほど効く。
- 一括変更は1社ごとに状態変更の活動を追記する。活動が溜まるほど活動の索引が育ち、同じ10万社でも遅くなる。測定は合成の活動を持つ保存先（密な分布で約220万件）から始め、一括変更でさらに増える。活動が1000万件を超える保存先では、余裕が減る。
- 重い一括変更を休まず繰り返すと、書き戻しの速さが律速になり、単発の時間より長くなる。`benchmarks.md` の参考値に載る。
- 他のアプリが読み取りを開いたままにすると、SQLite は WAL を巻き戻せない。背圧は `busy_timeout` まで待ったあと書き込みを進める。書き込みまで止めると、読み取りが続く間も活動の記録を待たせない（要件5.6）に反するため。歯止めは書き込み前の空き容量の確認。
- 測定の準備（深いページの位置決め）は SQL の `OFFSET` を使うので、DB の内部では位置に比例して走査する。通常の `list` の深いページとは別の処理。
- 担当者のメモの消去（`wipe_notes`）は、活動に `contact_id` の索引が無いため、活動の全件を走査する。活動の記録ごとの索引の更新を避けた代わりで、時間は未測定。
- 空き容量の見積りは近似。確定前の読み取り（旧キー、消去対象の件数、既存の行の大きさ）に基づくので、同時に別の書き込みが対象を変えると古くなりうる。見積りを超えて SQLite が空き不足で失敗しても、その書き込みは全体がロールバックされる。
- 登録・更新の時刻は実行時の壁時計で、注入できない。
