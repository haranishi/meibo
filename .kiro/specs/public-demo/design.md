# Design: 誰でも触れる公開デモ

## 設計判断
既存のhosted（`crates/app/src/hosted/`）に、起動時の明示の指定 `--public-demo` でだけ有効になるモードを足す。通常のhostedの認証・権限・保存は変えない（Req 7）。

| 論点 | 採用 | 捨てた案と理由 |
|---|---|---|
| 入室 | パスワードなしの「デモを開く」だけ。パスワードログインはデモ中は404 | 共有パスワード: ログイン失敗の数え方（利用者名ごと5回・全体100回、照合より前に判定）で、`curl` 5回で全員を締め出せる。Argon2の照合を公開で受けると、同時に多数来たとき、CPUとメモリを使い切る |
| session | 起動ごとに1つの共有session。入室は同じsessionを渡すだけで、増やさない | 訪問者ごとのsession（件数の上限つき）: 全員が同じ利用者でsessionに区別の意味がなく、少数の接続元が入室を繰り返すと、上限の追い出しで他の訪問者のsessionが消え、入室の全体の上限も使い切れる（独立レビューの指摘・2026-11-24）。logoutが共有sessionを消さないよう、デモでは保存先のsessionを消さずCookieだけ消す |
| 保存先 | 起動のたびに作り直す使い捨てのSQLite。外部の保存先は使わない | 招待制の構成（Worker・Container・Turso Cloud）: 保存先が要らないデモに、有料契約と外部サービスを足す。signupがなく誰でも入れない |
| 初期化 | アイドル15分・上限6時間でプロセスが終了し、実行先が再起動する | 常駐して定期にデータを戻す: 戻す処理の不具合と、止まったままになる危険が増える。終了は、どの実行先でも同じ動きになる |
| 共有範囲 | 全訪問者が同じ1組織を共有する | 訪問者ごとの使い捨て組織: 操作が混ざらない利点はあるが、組織の動的な作成と掃除が要る。混み合う実績が出てから足す |
| 遅い接続への備え | 製品側の自己終了（3.6）と、実行先の前段が本文を受け切ってから渡すこと | tiny_http の置き換え: 変更が大きい。tiny_http 0.12.0 はソケットの読み書きのタイムアウトを持たず、スレッドを上限なしに増やす（crateのソースで確認）。招待制では前段のプロキシが吸収していた。tiny_http は、拒否した要求でも宣言された長さの本文を読み捨てる（`EqualReader` の `Drop`。巨大な宣言長では確保に失敗して終了しうる）うえ、応答に `Connection` ヘッダーも付けられない（crateのソースで確認）。そのため、アプリを直接インターネットへ出さず、本文を受け切って宣言長と一致する要求だけを渡す前段を、公開の条件とする |

## 構成
```
訪問者 → Cloudflare（DNS・Worker）→ Container（meibo hosted --public-demo・HTTP・単一プロセス）
          ├ 静的な応答の保持・入室の頻度の制限・停止の切替
          └ Hostを公開ドメインのまま渡す                └ 使い捨てSQLite（組織 demo・合成データ）
```
起動の流れは、保存先の作成 → 組織と利用者の作成 → 初期データ → 待ち受け開始。待ち受けの行は、初期データの完了後に出す（実行先の起動確認が、準備の途中を通さない）。

## 製品側の変更
### 起動指定（Req 3.4・7）
`meibo hosted ROOT serve --origin URL --bind ADDR --public-demo [--demo-contact URL]`
- ROOTは、存在しないか、空のディレクトリ。中身があれば拒否する。実データ・永続領域・遠隔保存・複数組織を含む場合も同じ。
- `--access-config`・遠隔保存の設定との併用は拒否する。`--allow-http-loopback` は試験のために併用できる（既存どおりloopbackだけ）。
- 設定は起動引数だけで決め、保存済みの設定や要求の値では有効にしない（Req 7.2）。環境変数は増やさず、コンテナの起動コマンドが引数へ展開する。
- 既定値: アイドル900秒・上限21600秒・本文64KiB・保存先32MiB・入室300回/分・合成の取引先150社。sessionは共有の1つ。

### 入室と画面（Req 1・8・9）
- 未認証の `GET /` は `/login` へ302で進め、`GET /login` がデモ入口を返す。`login.html` のパスワード欄を「デモを開く」ボタンに置き換え、共有欄（X・LINE・コピー・端末の共有）は既存のpublic-entryを使う。titleとdescriptionはデモ用にする。画像は既存の `public-entry.png`。
- `POST /demo/enter`: 既存のHost・Origin・CSRFの検査を通した後、組織 `demo` の編集者 `demo` の共有sessionを渡して `/` へ進める。共有sessionの値は起動ごとに乱数で決めてメモリだけに持ち、保存先には要約だけを置く。入室のたびに期限とアイドルの時刻を更新する。全体の上限（入室300回/分）を超えたら429で「混み合っています」と返す。接続元ごとの制限は前段が担う。
- `POST /auth/login` は404。`/auth/logout` は残すが、共有sessionは消さずCookieだけを消す（他の訪問者を巻き込まないため）。
- 認証後の画面は、サーバーが返すHTMLに、画面上部の常時の注意書き（合成データ・15分操作がないと初期化・個人情報を入力しない・連絡先）と `/demo.css` を差し込む。概要の応答にデモの印は足さない。既存の「合成デモ」表示は残す。
- 初期化の後、または長く操作がなかった後に旧sessionで来たら、`/login?reset=1` へ戻し「デモが初期化されたか、しばらく操作がなかったため、入り直しが必要です。もう一度『デモを開く』を押してください。」と出す（Req 4.4）。

### 止める操作と上限（Req 3）
- 止める: `/api/import`・`/api/leads*`・`/api/lead-form`・`/api/activity-sync*`・`/forms/*`・利用者と所属の変更・実データ関連。理由つきの403か404を返し、画面の導線は隠す。
- 上限: 取引先1,000・活動5,000（取消を含む）・商談200・独自項目20・担当者2,000・仕事5,000・架電リスト50。保存量は、保存先（ROOT）配下のファイルの合計サイズ（SQLiteのWAL・共有メモリのファイルを含む）が32MiB以上になったら、書き込みのPOSTをすべて断る（経路を問わず効く）。断るときは「デモの保存量の上限に達しました。しばらくすると初期化されます」を返す。件数の上限は、作成する経路ごとに確かめる。保存量が上限に達したまま10秒続いたら、プロセスを終了して初期状態へ戻す（自己終了の④）。監査の記録は、デモでは書かない（Req 3.7）。
- 本文: Content-Lengthが明示された64KiB以下のPOSTだけ業務処理に渡す。分割転送・`Expect`・上限超過は、業務処理をせずに拒否する（3.5）。拒否した要求の本文の読み捨ては tiny_http に任される。前段が本文を受け切ることが前提になる。

### 自己終了（Req 4・3.6）
- 待ち受けは `recv_timeout(500ms)` の周回にし、各周回と各要求の後に「最後に動いた時刻」を更新する。
- 終了は4つ。①アイドル（`/health` を除く要求がない）②上限時間 ③見張りの検知（最後に動いた時刻から10秒以上）④保存量の上限（保存先の合計サイズを2秒ごとに測り、上限に達した状態が10秒続いたとき）。終了前に `demo-reset reason=idle|uptime|stalled|storage` を1行出し、終了コードは①②④が0・③が70。
- ③は、本文を遅く送る接続で単一の処理の流れが止まった場合と、待ち受けの異常（スレッドの生成失敗など）を拾う。見張りは別スレッドで、1秒ごとに確認する。
- 待ち受けの自己確認: 10秒ごとに自分のポートへ `GET /health`（`Host` は設定のもの）を送り、2秒以内に200が返らない状態が3回続いたら、同じく終了する（理由 stalled）。待ち受けのスレッドだけが失われた場合を拾う。過負荷で応答が遅れ続けた場合も、同じ判定で終了して初期状態へ戻る（過負荷からの自己回復として、そのまま採る）。
- 時間は起動引数 `--demo-idle-seconds`・`--demo-max-uptime-seconds`・`--demo-stall-seconds`（`--public-demo` のときだけ）で変えられる。既定は900・21600・10秒。試験と運用の調整のために置く。
- 終了と時刻の判定は、時刻と終了処理を差し込める小さな部品にして、実際に終了せずに試験する。

## 営業デモの初期データ（Req 2）
起動時刻（日本時間）を基準に、`hosted/demo.rs` が作る。外部の名簿や通信は使わない。
- 取引先: 既存の合成生成を150社。**すべて先頭に「合成・」を付ける**（生成器は「桜」「竹」「神」「風」などの断片の組み合わせで、実在の社名と偶然一致しうる）。電話番号は、生成器のランダムな番号（090などの実在しうる番号になりうる）を使わず、`000-0000-NNNN`（どの電話番号体系にも存在しない形）に置き換える。URLは生成器の `https://example.invalid/N` のまま使う。
- 利用者: `demo`（入室用・編集者）と `demo-b`（担当B・編集者）。2人の資格情報は乱数で作って保存せず、パスワードログインはデモ中は使えない。
- 商談9件（金額・段階・確度・担当は、紹介動画の撮影に使った合成DBと同じ）。今月に決着した受注1件（32万円）と失注1件（9万円）、今月見込みの未決着4件、来月見込みの未決着3件。見込日は起動日を基準にし、月末を超えない。
- 月次目標: 今月、`demo` が40万円・`demo-b` が20万円。
- 再架電: 期限が過ぎた1件（昨日の朝9時）を `demo` に付ける。
- 初期状態の月次集計は、受注額32万円・受注率50%・確度加重見込み65万円・着地予測97万円になる（動画と同じ値）。起動した時点では、起動日にかかわらず成り立つ。稼働中に日付や月をまたぐと「今月」の集計は変わる（上限6時間のため、月末の夜に起動した場合は、翌月の0時以降、今月の受注額が0円になる）。

## 実行物（Req 5・6）
- `Dockerfile` に `demo` ターゲットを足す。起動コマンドは `sh -c` で `MEIBO_DOMAIN`（必須）と `PORT`（既定4317）を展開し、起動のたびに新しい作業用ディレクトリ（`/tmp/meibo-demo-<時刻>-<pid>`）を指定して `meibo hosted ... serve --public-demo ...` を実行する。実行先の保存領域が再起動で消えない場合も、前回の残りに依存しない。
- `.github/workflows/demo-image.yml`: 手動実行と `demo-v*` タグで、linux/amd64のイメージを作り、公開と同じ起動引数で起動して、公開ゲート（検証 1から3）を通す。通ったことを確かめるための検査で、イメージの公開先（レジストリ）には置かない。配備は、検査済みの同じ版のソースから行う。
- `deploy/demo/cloudflare/`（新規）: デモ専用のWorker（小さな逆プロキシ）とwranglerの設定。
  - 公開側の `Host` を、そのままコンテナへ渡す（既存の `cloudflare/src/container.ts` と同じく明示する）。
  - 静的な応答（`/login.css`・`/login.js`・`/public-entry.*`）と入口（`/login`・300秒）は、Workerが一定時間保持する（Cookieを伴わない200の応答だけ。製品の応答は `no-store` のまま変えない）。保持した応答は、起動中のコンテナへ届かない。
  - `POST /demo/enter` を含むPOSTに、接続元ごとの頻度の制限を置く。接続元のキーは、IPv6なら先頭64ビット（/64）に丸める（1つの/64から無数のアドレスを作って制限を避けられないように）。
  - 停止の切替（設定値1つで、コンテナへ通さず「メンテナンス中」を返す）。
  - コンテナは1つだけ（`max_instances=1`）、無通信15分で休止（Durable Objectのアラームで止める。アラームは、起動後の最初の要求で設定し、発火時に最後の要求の時刻から設定し直す。要求のたびには書き込まない）。大きさは、起動後のメモリの実測で決める（`lite` 256MiB で足りる見込み）。
  - 既存の `cloudflare/` のWorker（Turso用の待ち行列・準備状態・復旧の仕組み）は使わない。デモは保存先が要らず、仕組みが大きく違うため。

## 実行先（Req 5）
**第1候補はCloudflare Containers（運用者の希望）。契約の承認は6.1で改めて取る。代替はFly.io（同じイメージで動く）。**

| 項目 | Cloudflare Containers | Fly.io（代替） |
|---|---|---|
| 固定費 | Workers Paid 月$5（約780円）。Containersの利用に必要。承認前は契約しない | なし。無料プランに、カード登録後、月$5の利用枠がある |
| 使用量の含み | メモリ25GiB時間・CPU375vCPU分・ディスク200GB時間・転送500GB（公式の料金ページ） | 256MBのマシンで月約$2.2〜2.5（常時起動の場合） |
| 常時起動の最悪（1台固定） | 月$9前後（公式の料金表の単価で計算: `lite` の256MiBとディスク2GBを730時間、CPUが常にフル稼働したとして、含まれる量を引いた超過分が約$4に、月$5を足す）。休止があれば、含まれる量の範囲（約100時間分）で$5のまま | 月$3前後。転送は別に1GBあたり$0.02〜0.04 |
| 自動で止まる請求の上限 | Containersの使用料は対象外（公式の説明・2026-11-24。費用の上限があるのはWorkersとDurable Objectsだけで、アカウント全体に効き、超えると同じアカウントの他のWorkerも止まる）。予算アラート（アカウント全体のメール通知・止まらない）、停止の切替、コンテナ1台の固定で守る | なし。台数の固定と通知で守る |
| 独自ドメイン | Workerのカスタムドメイン（同じアカウントのDNSに自動で追加される） | `fly certs` と、CloudflareのDNSの追加 |
| 新しい準備 | なし（既存のCloudflareアカウント）。wranglerとDockerが手元に要る | 新しいアカウント・カード・flyctl |

- 運用者が選んだ独自ドメイン（紹介のDayの番号を使う型のサブドメイン）で公開する。DNSの変更は、内容を見せて承認を得てから行う。
- Fly.ioを使う場合は、本文を受け切る前段（逆プロキシ）を別に用意する。直接公開は支持しない（上の「遅い接続への備え」）。
- 決めること（6.1）: 契約の承認、月額の上限と通知、停止と再開の手順。
- 選ぶ条件: 前段が遅い接続を受け止めること、東京かアジア、`Host` が公開ドメインのまま届くこと、使わないときは休止して初期化されること。

## 検証（Req 6）
1. Rustの試験（hosted）: 入室・404・禁止操作・上限・初期データの値・名前の接頭辞・時刻の判定・見張り・通常モードの回帰。
2. ブラウザ試験（390・768・1440px）: 入口 → ボタン → 再架電のある画面 → 架電モードで保存して翌日朝9時 → 商談ボード → 月次集計の値 → 注意書き → 共有欄。
3. 悪用の試験: 入室の連打（429と、先に入った訪問者のsessionが有効のままであること・logoutしても他の訪問者のsessionが残ること）、巨大・分割転送の本文、取り込みの拒否、本文を1バイトずつ送る接続で10秒以内に終了して復帰すること、保存量が上限に達したまま続くと終了すること。
4. 公開ゲート: 手順1から3の一部を、公開と同じ起動引数のイメージ（CI）と、配備後の公開URLの両方で流す。Hostが公開ドメインのまま届くこと、Workerの保持・頻度の制限・停止の切替も、ここで確かめる。公開URLでは、HTTPS・Host不一致の拒否・未認証APIの拒否・OGP・共有も確かめる。結果は `docs/public-demo-verification.md` に残す。

## 未決・リスク
- 実行先・費用・ドメイン・認証の承認（運用者）。
- 入口の連絡先 `--demo-contact` は、GitHubのIssuesを想定する。
- 全訪問者が1組織を共有するため、他の人の操作で表示が変わる。注意書きに明記する。
- 実行先の前段の挙動（本文の受け切り・タイムアウト）は、公開前の試験で実測する。
- 入室の全体上限（300回/分）は、前段の接続元ごとの上限（20回/分）では15以上の接続元があれば使い切れる。入室は1行の更新だけで軽いので、上限は、CPUの小さいコンテナを守る最後の備えとして置いている（それを超える規模の攻撃は、前段とCloudflareの防御に任せる）。
- 全訪問者が同じsessionと同じデータを共有するため、1人の訪問者がデータを消したり大量に書き込んだりできる。復旧は、アイドル・上限時間・保存量の上限による初期化に任せる。
- 応答をゆっくり受け取る接続が、Cloudflareの前段でどこまで溜まるかは未確認（公開URLで実測する）。Workersのレート制限は拠点ごとの結果整合で、数え方の精度は保証されない。
