# Design: 利用量と費用の目安

## ユーザーストーリー
運用者として、月の途中で「何にどれだけ使っているか」「無料枠と上限に近づいていないか」を
1画面で確かめ、増えていれば原因の機能を特定したい。

## UXの5階層
- 戦略: 費用の不安を数秒で解く。最優先は今月の目安額と無料枠の残り、次が原因の機能。
- 要件: 今月の目安額（上限があれば割合）、無料枠の使用率、機能別の内訳、日ごとの推移、数字の限界。
- 構造: 1ページ。上から「今月」→「無料枠」→「機能別」→「日ごと」→「この数字の見方」。入口は管理者の業務画面の上部。
- 骨格: 今月の目安額を大きく1つ。無料枠は割合の棒を項目ごと。機能別は推定額の多い順の表で、狭い幅では群・要求数・推定額だけを出し、残りは行を開いて見る。日ごとは棒の列。
- 表層: 既存の色・書体・余白を使う。色で目立たせるのは80%以上の警告だけ。数字は右にそろえる。

5層を通して決めたこと: ①表より先に今月の目安額と無料枠を置く ②80%以上は色と文で知らせる ③狭い幅では列を減らし、行を開いて詳細を見る。

## 集計
- `meibo-db`（cloud）: 接続ごとに往復数・読み取り行数・書き込み行数を足し、取り出すと0に戻す。値は Hrana の応答の `rows_read`・`rows_written`。提供者が返さない可能性は配備後に確かめ、画面の注記に反映する。
- app: 要求ごとに処理時間を測り、control と tenant の接続の値を取り出して、日（UTC+9）と群のメモリ上の集計に足す。429 と固定の応答も数える。
- 排他を取った要求は、前回の保存から60秒以上たつと、直近31日の未保存分を1つの `INSERT … ON CONFLICT … DO UPDATE` で足し込む。読み取りの速い経路は書かない。
- 業務の結果が確定した後の集計失敗では、その分を捨てて確定した応答を返す。通信断なら再送も排他の解除もせず、応答後にプロセスを終了する。

## 表と用意
`usage_daily(day TEXT, route TEXT, requests INTEGER, ms INTEGER, round_trips INTEGER, rows_read INTEGER, rows_written INTEGER, PRIMARY KEY(day,route))`。
- `init`（と復旧先の初期化）で作る。既存の control は `hosted-remote CONFIG usage-enable` で作る（排他の中・何度実行しても同じ）。
- 起動時に表の有無を読む。表がなければ、管理者が利用量のAPIを開いたときに読み直し、表ができていれば集計を始める。`SCHEMA_PROBE` と保存の許可表は変えない。

## 推定
- 秒 = 要求ごとの処理時間を100ミリ秒に切り上げて合計。
- Cloud Run: vCPU 1 × $0.000024/秒、メモリ 0.5GiB × $0.0000025/GiB秒、要求 $0.40/100万（2026-11-26確認）。
- 無料枠（請求先あたり・月）: 180,000 vCPU秒、360,000 GiB秒、200万要求。Turso: 読み取り5億行、書き込み1,000万行。
- 円は 1ドル=155円で換算した目安と明記する。月の上限は環境変数 `MEIBO_USAGE_CAP_JPY`（任意）。
- 定数は1つのモジュールに置き、確認日を書く。

## 画面とAPI
- `GET /api/admin/usage`: admin のみ。DBの直近31日と未保存分を合わせて返す。速い経路で読み、書かない。
- `GET /usage`: admin のみの固定ページ（`usage.html`・`usage.js`・`usage.css`）。CSP は変えない。値は `textContent` で入れる。
- 業務画面の HTML は、遠隔保存の admin にだけ入口を差し込む。

## 捨てた案
- Cloud Logging から集計: 権限と外部APIが要り、機能別の行数が取れない。
- 要求ごとに保存: 書き込みと往復が増える。
- 正確な請求額の表示: Cloud Billing の出力の設定と権限が要る。目安で足りる。

## 変えないもの
認証・権限・排他・結果不明の扱い、手元版とローカルhosted版、準備確認の条件。

## 実装で設計から変えた点（2026-11-27）
- 往復と行数は接続ごとでなく、`meibo_db::RemoteUsage` のスレッドごとの計数にした。要求の途中で開いて捨てる接続（`open_tenant` の確認など）も数えるため。サーバーは1スレッドで要求を順に処理する。
- 表の `ms` は、要求ごとに100ミリ秒へ切り上げた処理時間を保存する（推定の単位と同じ）。実際の処理時間は残らない。
- 最初の要求の時刻から60秒の窓を数える。速い経路だけが続く間は保存されず、画面に未保存の件数を出す。
- `/usage` と部品（`usage.js`・`usage.css`）も admin のみ。session が無い `/usage` は `/login` へ移す。
- 日ごとの棒は見るだけ（幅390pxで指の大きさを取れないため）。最大の日と今日の棒に金額を付け、数字は表で出す（最初は直近7日、「すべて表示」で31日）。
- 入口は2つ。640px以上は上部の行のボタン、どの幅でもアプリメニューの末尾のリンク。640px未満は上部のボタンを隠し、検索欄の幅を改修前と同じにする。`login.js` が上部を組み直すときも入口を残し、メニューのリンクを末尾へ移す。
- 画面採点を受けた変更（2026-11-27）: 今月の枠は結論の文（無料枠の内側／月末に超える見込み／80%以上／超過）を先に置き、無料枠を引いた後の請求の見込みを大きく出す。引く前の目安は見出しを付けて小さく出す。上限額の割合は引く前の目安で計算する。
- 管理者でない利用者が `/usage` を開くと、HTMLの「管理者だけが開ける画面です」を403で返す（監査は同じ。APIはJSONのまま）。その画面のため `usage.css` は会員なら誰でも読める（データを含まない）。`usage.js` と API は admin のみ。
- 無料枠の超過はサーバーが丸める前に判定する。見込みが正なら1円未満も表示する。10円未満は小数1桁、10円以上は整数にそろえる。機能別は要求0件の群を省き、その旨を書く。開閉は右端の専用の列のボタン（44px以上）。
- 画面を離れたら取得済みの数値と表示を消す。復帰時と別タブでの認証変更時は、現在の利用者の管理権限と context を確かめてから表示する。
