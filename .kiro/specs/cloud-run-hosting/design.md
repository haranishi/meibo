# 設計: Cloud Run と Turso の自分用公開

## 構成

```text
ブラウザ → Cloud Run（asia-northeast1・最大1台） → Turso Cloud（東京・control と組織DB）
```

- 実行物は既存の `cloudflare/Dockerfile`（linux/amd64・`cloud` feature）と `cloudflare/entrypoint.sh` を使う。
- `MEIBO_ORIGIN` と `MEIBO_REMOTE_CONFIG`（環境変数名だけを持つ）は環境変数で渡す。
- DB の URL と鍵は Secret Manager から環境変数へ渡す。
- 公開URLは `https://<サービス名>-<プロジェクト番号>.<地域>.run.app` の固定の形を使い、これを `MEIBO_ORIGIN` にする。

## 環境（2026-11-27）

| 環境 | 場所 | データ | 入口 | 支出上限 |
|---|---|---|---|---|
| 作る | 運用者の端末 | 合成 | 手元のみ | なし |
| 確認用 | Cloud Run と Turso | 合成 | 公開URL＋アプリのログイン | 月100円 |
| 本番 | 別プロジェクトの Cloud Run と Turso | 実データ | Identity-Aware Proxy＋アプリのログイン | 月400円 |

- 本番の Identity-Aware Proxy は Cloud Run に直接付ける。組織の無いプロジェクトでは、独自の OAuth クライアントを一度作る必要がある（同意画面は External）。
- 配備時に確かめる: IAP の Cookie とアプリの Cookie の合計が上限（8KB）を超えないこと、画面の通信で認証が切れたときの返り方、応答時間の増え方。

## 管理の道具（2026-11-27）

- 管理命令は `cargo xtask cloud-run-admin` で実行する。`gcloud run services describe` の形の設定から参照名と鍵の参照を読み、鍵は子プロセスの環境にだけ置く。ビルドは鍵を読む前に行う。
- シェルや Python の別の道具にせず、リポジトリの Rust の作業用コマンドに置く。依存は増やさない。
- 初回はサービスの代わりに同じ形の記述ファイルを渡す。

## 判断と捨てた案

- Cloudflare Containers: 設計済みだが有料プランが要るので、無料枠を基本にする今回は使わない。
- 小さな仮想サーバーと手元型の SQLite: 速く、第三者へ提供する段階の第一候補。月額がかかるので今回は使わない。
- Render の無料枠: 休止と起動待ちがあり、公式に本番向きでないと書かれている。

## 費用の守り（2026-11-26 に公式文書で確認）

- 支出上限（Cloud Billing の spend cap・2026-10-13 に正式版）は、1プロジェクトの Cloud Run を対象にする。
- 判定は無料分とクレジットを引く前の定価で行う。反映に時間差があり、超えた分は請求される。
- 上限の対象外の保存（コンテナイメージ）は、古い版を自動で消して無料枠に収める。通信料は少額かかる可能性がある。上限の判定に含まれるかは公式文書で確認できていない。
- 反映は1日以上遅れ得る。公開URLへの大量アクセスは、本番では Identity-Aware Proxy で止め、確認用では remote-performance 要件3.6の制限で抑える。
- Secret Manager の無料は、請求先あたり有効な版6つまで。本番は鍵だけを置く。

## 既知の限界

- 依頼は1件ずつ処理する。重い操作の間は他の操作が待つ。
- 全要求で保存先の全体の鍵（gate）を取る。処理の途中で止まると、手動の `gate-recover` が要る。
- Turso の利用規約（2024年3月版）は第三者のための利用を認めない。運用者自身の利用に限る。
- 確認用の公開URLは誰でも開ける。アプリのログインで守る。故意の誤入力でログインが一時停止され得る。遅い送信で処理がふさがる可能性は残る。
- 永続ディスクが無いので、メール・予定の連携は使わない。
